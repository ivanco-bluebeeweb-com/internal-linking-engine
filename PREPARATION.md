# Internal Linking Engine — PREPARATION.md

## 1. Паспорт приложения

- **Название**: Internal Linking Engine
- **Короткое описание**: движок, который для каждого подключённого сайта сам понимает
  смысл всего контента, находит релевантные материалы для перелинковки и органично
  вставляет анкоры + один CTA-блок на конверсионную страницу — с обязательным
  preview→apply и откатом.
- **Владелец продукта**: Imperal Cloud (внутренний продукт, встроенная платформенная фича)
- **Дата и версия подготовки**: 2026-08-29, v1 (Discovery)
- **Почему создаётся сейчас**: органичная перелинковка + CTA сейчас делается вручную,
  внутри сессии (пилот: climtec.md, статья про рекуператоры). План
  `~/Downloads/План разработки — движок внутренней перелинковки (Internal Linking Engine).md`
  требует превратить это в автоматическую платформенную фичу, работающую out-of-the-box
  на любом числе подключённых сайтов без участия человека в каждом отдельном случае.
- **Связанный pilot**: climtec.md (рекуператоры) — источник урока про языковую изоляцию
  (RU↔RO нельзя мешать).
- **Задача в BBW Imperal Apps**: #2791 `[App Development] Internal Linking Engine`
  (проект 97), создана по образцу #2149/#2143.

## 2. Проблема в человеческих словах

Когда **редактор контента (или сама Webbee от имени пользователя)** сталкивается с
**новой или уже опубликованной статьёй, которая логически связана с другими
материалами сайта**, ей приходится **вручную читать весь корпус статей, вспоминать,
какие из них релевантны, руками выбирать анкорный текст и руками добавлять один CTA
на каталог/услугу** — из-за чего возникает **непоследовательная перелинковка
(разные статьи получают разное качество ссылок в зависимости от того, кто и когда
их правил), упущенный SEO-эффект на сайтах, где такой ручной проход никогда не
происходит, и риск испортить разметку (Gutenberg/Bricks) при неаккуратной вставке**.

Существующие инструменты не закрывают это:
- `wordpress-hub.extract_links` только **читает** уже существующие ссылки — не строит
  граф релевантности и не предлагает, что добавить;
- `wordpress-hub.replace_post_content_text` — безопасный примитив точечной правки,
  но не решает, ГДЕ и НА ЧТО ссылаться;
- `content-strategy-app.check_keyword_cannibalization` — про конфликт статей за одно
  ключевое слово, не про перелинковку;
- `seo-audit-engine` — только диагностирует технические проблемы, не чинит контент.

## 3. Границы (что это НЕ делает)

- НЕ публикует контент и не создаёт статьи — это `wordpress-hub` / `imperal-article-writer-extension`.
- НЕ решает, какой контент писать дальше — это `content-strategy-app`.
- НЕ делает общий технический SEO-аудит сайта — это `seo-audit-engine` (только один
  специфичный finding-тип: "статья без внутренних ссылок"/"нет CTA").
- НЕ пишет напрямую в WordPress своими руками — фактическую запись всегда делает
  `wordpress-hub` (`replace_post_content_text`/`update_post`), Internal Linking Engine
  только строит план (diff) и вызывает запись через оркестрацию в чате/фоновой задаче.
- Экосистемное правило (Content Strategy Hub уже следует ему): **приложение не вызывает
  другое приложение напрямую** — Webbee сама передаёт данные между вызовами в одном
  чате/фоновой задаче. Internal Linking Engine придерживается того же контракта.

## 4. Архитектура (компоненты)

1. **Content Indexer** — для каждого зарегистрированного сайта хранит: список
   постов/страниц (id, title, slug, url, post_type, categories/tags, product_type,
   Polylang-язык), их текстовый "профиль" (заголовок + первые N символов + категории/теги
   как proxy-сигнал темы — см. §5 почему НЕ полноценные embeddings), и текущий граф
   исходящих ссылок (через `extract_links`, читается лениво при сканировании).
2. **Relevance Engine** — по метаданным + текстовому пересечению считает top-2..5
   релевантных целей для каждой статьи. Жёсткое правило: **никогда не смешивать языки**
   (RU→RU, RO→RO — урок climtec.md).
3. **Anchor Placement Engine** — LLM-проход (`ctx.ai.complete`) по параграфам исходной
   статьи с промптом: "не выдумывай факты, вставляй ссылку только там, где это
   семантически логично, максимум N ссылок на статью, не трогай остальной текст,
   верни только exact-substring находки + предлагаемый анкор". Результат — список
   `(find_exact_substring, replacement_with_anchor)`, каждый проверяется на
   единственность вхождения перед использованием (тот же контракт, что и
   `replace_post_content_text`: "find must match EXACTLY ONCE").
4. **CTA Composer** — отдельный консервативный модуль: 1 блок на статью, шаблонизирован
   по нише/тону сайта (из `site_profile`, который Webbee получает из
   content-strategy-app и передаёт как вход — не прямой вызов), не более одного
   добавления на статью за прогон.
5. **Diff & Safety Layer** — preview/apply 1-в-1 паттерн (уже стандарт в wordpress-hub
   bulk-инструментах):
   - `preview_internal_links(site_id, post_ids?)` → JSON-диф: что добавится, куда,
     state_token поста (используем `expected_state_token`, как во всех
     `preview_bulk_*`/`apply_bulk_*` wordpress-hub функциях).
   - `apply_internal_links(site_id, post_id, expected_state_token, plan_id)` — Webbee
     передаёт диф в `wordpress-hub.replace_post_content_text` за пределами этого
     приложения; здесь фиксируется факт применения + возможность отката
     (перезаписью на сохранённый оригинал через тот же `replace_post_content_text`).
6. **Scheduler/Orchestrator** — периодический тик (тот же паттерн, что
   `seo-audit-engine`/`Page Speed Insights`: `@ext.schedule(..., TICK_CRON)` + настройка
   часа/дней в хранилище, не жёсткий cron) — рескан сайта при появлении нового
   контента, чтобы новые статьи могли стать целями ссылок из старых.

## 5. Модель данных (rationale для выбора без embeddings-инфраструктуры)

Стек всех существующих приложений (`Content Strategy Hub`, `SEO Audit Engine`,
`WordPress Hub`, коннекторы) используют только `imperal-sdk` (+ иногда `pydantic`) в
`requirements.txt` — нет numpy/sklearn/sentence-transformers нигде в портфеле.
Полноценные векторные embeddings потребовали бы новую тяжёлую зависимость и
внешний embedding-провайдер, которого сейчас нет ни у одного приложения. Вместо
этого Relevance Engine на MVP использует **детерминированный метаданно-текстовый
сигнал** (категории/теги/product_type/язык как жёсткие фильтры + пересечение
значимых слов заголовка/эксцерпта как ранжирующий скор) — это дешевле, объяснимее,
не требует новой инфраструктуры и уже похоже по духу на `check_keyword_cannibalization`
в Content Strategy Hub. Embeddings остаются явным пунктом roadmap (см. §11), если
метаданно-сигнала окажется недостаточно на реальных сайтах.

Коллекции (через `ctx.store`, тот же паттерн, что Sites Registry/SEO Audit Engine):

- `ile_site_settings` — по сайту: включено/выключено, режим (`review_first`/`full_auto`),
  лимит ссылок на статью, CTA-цели (url + текст-шаблон + тон), исключённые страницы
  (никогда не трогать), список языков.
- `ile_content_index` — на статью: post_id, site_id, title, slug, url, post_type,
  categories, tags, product_type, lang, excerpt, last_indexed_at, outbound_links
  (кэш от extract_links).
- `ile_linking_plans` — один прогон = один план: site_id, created_at, per-post diffs
  (anchor-вставки + CTA), status (`pending_review`/`applied`/`rolled_back`/`rejected`),
  expected_state_token на пост, оригинальный текст (для отката).
- `ile_linking_runs` — дашборд прогонов: сайт, дата, добавлено ссылок/CTA, статус.

## 6. Guardrails (безопасность контента)

- **Языковая изоляция жёсткая, без исключений**: RU-статья линкуется только на RU,
  RO только на RO и т.д. (Polylang lang как обязательный фильтр в Relevance Engine,
  не рекомендация).
- **Лимит ссылок на статью** (по умолчанию 2-5, настраивается по сайту) — никогда не
  спамить.
- **Exact-substring-once контракт**: любая вставка анкора проверяется на единственность
  вхождения перед записью — то же самое железное правило, что уже действует в
  `replace_post_content_text`. Если LLM предложил substring, которого нет ровно один
  раз в тексте — предложение отбрасывается, не гадаем какое вхождение имелось в виду.
- **Не трогать остальной текст** — Anchor Placement Engine и CTA Composer работают
  только через `replace_post_content_text`-совместимые точечные правки, никогда не
  через полную перезапись/rebuild блоков (чтобы не рисковать Gutenberg/Bricks-разметкой).
- **Список исключений по сайту** — страницы, которые никогда не трогаем (например
  юридические/checkout/о нас).
- **Preview обязателен перед apply** — ни один прогон не пишет в контент без явного
  `apply_internal_links` с подтверждённым `expected_state_token`.
- **Откат** — план хранит оригинальный текст каждого затронутого фрагмента; откат —
  запись оригинала обратно через тот же `replace_post_content_text`.
- **Не выдумывать факты** — LLM-промпт Anchor Placement Engine и CTA Composer явно
  запрещает придумывать что-либо не присутствующее в реальном контенте/site_profile.

## 7. MVP-скоуп (release scope = максимум, подтверждено стандартной директивой
пользователя "максимум / все функции" — фиксируется без повторного вопроса)

Т.к. пользователь уже установил стандартное правило "максимальный функционал, полный
максимум" для новых приложений в этой сессии, Internal Linking Engine реализуется с
полным функционалом плана (Этапы 0-4 roadmap ниже в одном release), НЕ обрезанным до
голого MVP из Этапа 1. Ограничение на WordPress Hub сайты в первом релизе остаётся,
т.к. Webflow/Shopify write-примитивы для точечной правки текста статьи (аналог
`replace_post_content_text`) сейчас не существуют в этих коннекторах — это честная
техническая граница, не сокращение функционала по выбору.

## 8. Интеграции с существующими приложениями (все — через Webbee-оркестрацию в чате,
НЕ прямые вызовы приложение→приложение)

- **wordpress-hub**: `extract_links` (аудит текущих ссылок при индексации),
  `replace_post_content_text` (фактическая запись анкоров/CTA), `list_posts`/
  `get_post_content`/`get_post_meta` (индексация), `update_post` (если нужно поменять
  статус после правки).
- **content-strategy-app**: `site_profile` как источник тона/бренда/ниши для CTA;
  опционально Webbee инициирует рескан при `create_brief`/`link_external_article`.
- **seo-audit-engine**: новый finding-тип "статья без внутренних ссылок"/"нет CTA" —
  Internal Linking Engine закрывает эти findings по запросу Webbee.
- **google-search-console-connector / dataforseo-connector**: сигнал приоритезации,
  какие страницы важнее усиливать ссылками (передаётся как вход в `preview_internal_links`).
- **sites-registry**: единый источник списка сайтов независимо от платформы.

## 9. UX в панели Imperal

1. Настройки по сайту: включить/выключить, целевые CTA-ссылки, лимиты ссылок на статью,
   исключения, языки.
2. Дашборд прогонов (`ile_linking_runs`): сайт, дата, добавлено ссылок/CTA, статус,
   кнопка "откатить".
3. Ручной триггер "просканировать сейчас" + предпросмотр diff перед применением.
4. Режимы: **Review-first** (по умолчанию для новых сайтов) / **Full-auto**
   (переключение вручную после N успешных ручных подтверждений).

### Дальнейшее развитие (после первого релиза) и почему

| Направление | Почему |
|---|---|
| Полноценные embeddings вместо метаданно-сигнала | Если метаданных (категории/теги/product_type) окажется недостаточно для точной релевантности на сайтах с бедной таксономией — нужен реальный семантический сигнал. |
| Webflow/Shopify точечная правка контента | Сейчас нет write-примитива уровня `replace_post_content_text` в этих коннекторах — как только появится, Internal Linking Engine расширяется без изменения своей архитектуры. |
| Приоритизация по GSC/DataForSEO живым данным | Уже спроектировано как вход, но полноценная авто-подтяжка сигналов — отдельный срез. |
| Обучение на подтверждениях (доверие для full-auto) | Roadmap явно предполагает "переключение на Full-auto после N успешных подтверждений" — нужен счётчик и порог, не жёстко зашитый в MVP. |

## 11. Риски

- LLM может предложить substring, которого нет ровно один раз — митигируется жёстким
  exact-once контрактом (отбрасываем, не гадаем).
  - Смешение языков при недостаточных Polylang-метаданных на старых сайтах —
  митигируется: если lang не определён надёжно, статья исключается из целей/источников,
  а не линкуется наугад.
- Слишком агрессивная вставка (спам) — митигируется жёстким лимитом на статью и
  Review-first по умолчанию.
- CTA звучит навязчиво/не в тон — митигируется привязкой к `site_profile` (тон уже
  задаётся владельцем сайта в Content Strategy Hub), не выдумываем тон с нуля.

## 12. Live-критерии воплощения

Публичный Git-репозиторий с первого push, секреты проверены перед push (нет ключей,
т.к. это приложение вообще не хранит внешних credentials — работает только через
чужие уже подключённые сайты и store). Только `live verified` статус в таблице §10
считается доказательством реальной функции.
